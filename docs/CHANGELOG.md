## v1.18.4 · 504 根治（nginx 侧）：上游失败重试 + keepalive
**2026-11-18 09:56**

### 第四次 504 的现场
- 本机服务 200/6ms ✓；ECS→Mac **5/5 200（17-25ms）** ✓
- 但 **我 SSH 到 ECS 也超时了一次** ✗ —— 说明**Mac 出方向 Tailscale 也在丢包** ✓（与用户浏览器同源）
- Mac load **9.5**：WindowServer 50% + Chrome 47% + **FileProvider 37% + CloudKitDaemon 19% + iCloudDriveCore 19%** ✗
→ 结论：**iCloud 同步突发**（当天新增 5 本 + 我测试拉取 139MB/6MB 引发）把 Mac 网络打满 ✗ → Tailscale 偶发丢 SYN ✗ → nginx 等不到上游 → **504** ✓

### 修复（nginx 层，不再依赖 Mac 侧"恰好不丢包"）
```nginx
upstream ebm_backend { server 100.71.251.38:6722 max_fails=0; keepalive 32; }

proxy_pass http://ebm_backend;
proxy_set_header Connection "";
proxy_connect_timeout 10s;          # 单次建连上限（丢包快速失败）
proxy_next_upstream error timeout http_502 http_503 http_504;
proxy_next_upstream_tries 3;        # 丢一次 SYN 就重试，最多 3 次
proxy_next_upstream_timeout 30s;
```
- **keepalive 32**：减少握手次数（每次握手都是一次可能丢包的 SYN）
- **失败重试**：把"丢包 → 504"变成"丢包 → 重试 → 通常成功"

### 验证（iCloud 仍在同步、load 9.9 的情况下）
- 公网连续 **8/8 = 200** ✓
- **并发 20 = 全部 200** ✓
- `nginx -T` 确认 upstream/retry 已生效 ✓
- 备份：`ebm.drwen.cn.conf.bak-20261118-095600` / `ebm_proxy.inc.bak-20261118-095600` ✓

### 经验
**504 的四种成因（按出现顺序）**：
1. Conntrack/并发上限（`limit_conn 16` → 128）✓ v1.15.1
2. connect 超时过短（5s → 30s → 10s+重试）✓ v1.16.1/1.16.6
3. 批量 iCloud 取回挤占带宽（→ 限速 + 夜间）✓ v1.16.6
4. **上游偶发丢包**（→ nginx 重试 + keepalive）✓ **本次**
→ 现在无论 Mac 侧短时抖动，公网都能靠重试恢复 ✓

1. `search_queries()` 把书名按空白拆成**碎片查询词**（`更壮`/`更瘦`/`更强`/**`身体革命`**），

3. `douban_pick()` 的排序键是 `(score, seg_idx)` —— **作者是否匹配完全没有参与排序** ✗，
   于是 92 分的错书压过正确书；片段匹配（92/89）也不要求作者佐证 ✗

## v1.9.9 · 更正：下载失败不是"限流"，是脚本「不重试直链 + 网盘通道失效」
**2026-10-22**

### 用户质疑（判断正确）
"这个网站除非一天内大量下载，否则登录条件下不会限流，一定另有原因。"

### 复查：手工复现直接推翻了"限流"结论
用脚本自己的登录态与请求路径，分别请求**失败书(23488)** 与**成功书(23490)**：

| ctfile `get_file_url.php` | **0 字节** | **0 字节（同样为空！）** |

→ 结论：**直链本来是好的**；ctfile 通道对所有书都拿不到 URL（含"成功"的书），与"限流"无关。
真正的两个原因：
1. **站点偶发**对 `vipdown.php` 返回 HTML 页（疑风控/中转页）而非 PDF —— 今天 08:00 巡检里 23494 就是这样失败，而 08:08 的重试轮**立刻成功** ✓（日志可证）

### 修复（`yabook_watch/download_books.py`）
- 直链失败后**先重试直链 3 次（20s/40s 递增间隔）**，仍失败才转网盘 ❶
- 直链返回非 PDF 时，错误信息带上 **HTTP 状态 + Content-Type + 页面标题**（不再猜"可能需登录/配额"）
- ctfile 空响应文案改为 **`空响应(HTTP 200, 接口未返回URL)`**，并注释说明**并非限流**、该通道当前对所有书失效、仅作最后兜底

## v1.9 · 推荐清单的量级分析与历史归档（保持有界 + 不丢历史）
**2026-10-12**

### 用户提出
`_推荐待确认.md` 攒着历史与信息，量级大了会不会变慢？是否需要定期拆分/归档，让文件始终不超过一个处理量？

### 实测结论（不是估算）
| 事实 | 数值 |
|---|---|
| 管道 `recommend.py sync()` 对「已处理」区的保留上限 | **200 条**（`processed[-200:]`，第 201 条起被静默丢弃）→ **文件本身有界，不会无限增长** |
| 当前清单 | 25.2 KB / 155 行（已处理 135 条） |
| 单条已处理记录 | 平均 87 字符（单行） |
| 单条待确认 | 平均 290 字符（含作者/简介明细行） |
| 稳态推算 | 200 条已处理(≈17KB) + 100 条待确认(≈28KB) ≈ **47.5 KB / 530 行**；即使 200 条待确认也只有 76 KB / 830 行 |
| 解析/同步成本 | 一次线性扫描，千行内 **亚毫秒**；真正的延迟是 iCloud 往返（百毫秒级），与文件大小几乎无关 |

### 量级阈值（何时需要变更处理方式）
| 指标 | 舒适 | 注意 | 必须处理 |
|---|---|---|---|
| 主清单文件 | **< 50 KB** | 50–200 KB | **> 200 KB** |
| 待确认条目 | **< 50** | 50–100 | **> 100**（决策效率下降，不是性能） |
| 已处理历史 | ≤200 条（管道上限，自动） | — | 需要追溯更久 → 依赖归档 |
| 解析/sync 耗时 | **< 5 ms** | 10–50 ms | > 200 ms（届时才值得换存储） |
