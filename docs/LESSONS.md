# 经验教训与工程约定（LESSONS）

记录这个项目里**踩过的坑**和由此形成的约定。改代码前花五分钟读一遍，能省掉几小时。

---

## 一、验证方法论（最贵的一课）

### 1. DOM 正确 ≠ 屏幕正确：必须做像素级验证
**事故**：阅读页"渲染完成、日志正常、零报错"，但用户什么都看不到——`read.html` 自带样式却漏定义 `.hidden` 类，EPUB 白底容器永久盖住 PDF。
**当时为什么没发现**：所有自动化断言都在查 DOM（canvas 存在、占位 124 个、pageinfo 正确），没有一个在看屏幕。
**约定**：
- 前端可视性问题**必须**有像素/几何断言（本项目用 `scripts/ui-check.mjs`：截图像素统计 + `getBoundingClientRect` 几何检查）
- 用 `elementFromPoint` 验证"最顶层元素是谁"，专门抓"被其他层盖住"

### 2. 测试要能抓住真实故障，而不是"证明代码跑过"
- 反例：`assert(canvasCount >= 1)` —— 白屏时也通过
- 正例：`assert(card.scrollWidth <= card.clientWidth + 1)`（抓挤压）、`assert(同一行按钮 top 相同)`（抓对不齐）、`assert(canvas 采样非白像素 > 0)`（抓空白）、`assert(目录行数 >= 4)`（抓一整段）
- **写断言时问一句：这个断言在 bug 存在时会失败吗？**

### 3. 用隔离实例做端到端测试
`test/helper.js` 起真实进程 + 临时书库 + 临时数据目录 + 独立端口，`EBM_EAGER_COVERS=0`：
- 不碰真实书库与 `yabook_watch`（可以在真实服务运行时随便跑）
- 夹具要**模拟真实数据形态**：生成的合法多页 PDF（能真被 pdf.js 解析）、压平无换行的目录、含 HTML 实体的简介、`post_details.json` 元数据

### 4. 断言写错比不写更浪费时间
本次出现过 4 次"测试失败但代码是对的"：`i%120` 的期望值算错、`-webkit-line-clamp` 下用 `scrollHeight` 判断行数（该用 `getBoundingClientRect().height`）、在错误的视图里查 `#grid`、夹具的简介只有 137 字却断言 >300。**失败先问"是代码错还是断言错"。**

### 5. 测试脚手架自己也会写错
- 模板字符串里写 `'\n'` 会被当成真换行注入到被求值的 JS 里 → 应写 `'\\n'`
- `offsetParent` 对 `position:fixed` 元素恒为 null → 不能用它判断可见性
- 无头 Chrome 需要可写的 `--user-data-dir` 与显式等待调试端口就绪

## 二、前端坑

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `body { height: 100% }` | 顶栏 `position: sticky` 失效（滚动后搜索框消失） | `html{height:100%}` + `body{min-height:100%}` |
| 多个子元素各自 `sticky` | 侧边栏"书架/分类"两组滚动时叠在一起 | **容器整体 sticky**（`max-height` + `overflow-y:auto`） |
| `-webkit-line-clamp` + `scrollHeight` | 误判"文字超出行数" | 用 `getBoundingClientRect().height` |
| 弹性布局里塞太多按钮 | 卡片按钮被挤压变形 | 固定操作行：`margin-top:auto` + 主按钮 `flex:1` + 次按钮 `flex:0 0 auto` + `white-space:nowrap` |
| 静态资源无缓存头 | 改了 JS 用户看不到（启发式缓存） | 壳文件 `Cache-Control: no-cache` + 脚本 `?v=N` |
| 一次渲染上千 DOM | iPad 卡顿 | 首屏 120 + `IntersectionObserver` 自动追加 |
| 搜索与筛选叠加 | "书莫名搜不到" | 有搜索词时按**全库**搜索（暂忽略筛选）并明确提示 |
| 大字段进列表接口 | 首屏 447KB→更大 | 列表轻量 + `/api/book` 单本按需拉取 |

## 三、数据与管道坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 源数据的 HTML 实体 | 简介显示成 `&ldquo;` 字样（292 本） | 服务端"命名实体表 + 数字实体"解码，前端兜底 |
| 目录在源数据里零换行 | 目录显示成一整段（433 本全是） | `formatToc()` 按 卷/章/编号/页锚 分行 + 剔除抓取垃圾 + 超长行给出说明 |
| 管道 `state.json` 记录旧文件名 | 改名后 64 本书元数据失联 | 匹配时对文件名做**标记归一化**（`normBase`） |
| `library_files.txt` 缓存 | 管道可能误判"库里没有" | 每次下载前自动重建；查重用去掉括号标点的规范化书名，与标记无关 |
| 扫描版 PDF 无文本层 | 无法提取文字/目录 | 查 PDF 内嵌书签；书签只有页码时在阅读器折叠为"按页跳转"网格 |
| 元数据覆盖仅 19% | 大多数书详情页没有简介 | UI 明示；如需覆盖率提升要走独立方案（元数据补全/OCR） |

## 四、iCloud（策略 A）坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 直接读 dataless 文件 | `EAGAIN` / 0 字节下载 | 检测 `st_blocks===0` → `brctl download` + 探针轮询 → 202 流程 |
| 沙箱进程读 dataless | `sandbox initialization failed`（`qlmanage`）、`Resource deadlock avoided` | 用不沙箱的 launchd 服务；封面用 `sips` 而不是 `qlmanage` |
| 跨卷移动 dataless 文件 | `mv`/`shutil.move` 退化为复制 → 读取失败 | 用 **Finder 删除**（iCloud 感知）：`osascript -e 'tell application "Finder" to delete (POSIX file "…" as alias)'` |
| 重命名 dataless 文件 | 担心触发下载 | **不会**：实测 `blocks` 前后均为 0，size/mtime 不变（属元数据操作） |
| 系统自动驱逐本地副本 | 本地 121 → 54，封面变占位块 | 属 macOS「优化储存空间」正常行为，不是故障；打开即取回 |
| 批量下载诱惑 | 13.7GB 云端书 | **红线**：任何自动行为（封面/书架/OPDS/目录）都不得触发取回 |

## 五、运维坑

| 坑 | 现象 | 处理 |
|---|---|---|
| SIGTERM 兜底落盘 | 手动改 `shelves.json` 被内存态覆盖 | `launchctl bootout` → 确认进程退出 → 改文件 → `bootstrap` |
| nginx 重启 | 可能影响邻居站点 | 一律 `nginx -t && systemctl reload nginx`，**不 restart** |
| htpasswd 权限 | 认证后 500（worker 读不到文件） | `chown root:nginx; chmod 640` |
| 密码文件混淆 | 把 `$apr1$…` 哈希当密码用 | `.htpasswd_ebm` 存哈希；`.ebm_auth_note` 存用户名+明文（给人看） |
| MagicDNS 不稳定 | `ssh <ecs-host>` 以本机用户名登录被拒 | 用 `ssh root@<ecs-host>` 或 `ssh root@<ecs-ip>` |
| 公网爆破扫描 | 日志里 `admin`/`default` 等用户名轮番尝试 | nginx 限速（匿名按 IP，认证不限速）；必要时加 fail2ban |
| 无 git 仓库 | 改坏了没法 diff/回滚 | 重大改动前拍快照（`ebm/.snapshot-<日期>/` + `RESTORE.md`），批量数据操作必须有映射文件与回滚脚本 |

## 六、协作/需求坑

- **交互设计不要猜**：我曾按"每屏 120 张 + 显示更多按钮"实现，用户的预期是"滚到底自动加载"。涉及交互方式（按钮 vs 自动、弹层 vs 独立页）时先确认一句，省一轮返工。
- **先给事实再给方案**：用户问"目录为什么看不出条目形状"，先查清源数据（433 本目录零换行、PDF 书签 305 个是纯页码、正文无文本层），再决定"能修什么、修不了什么"，而不是先改代码。
- **做完就说清边界**：哪些是修好了、哪些是数据本身的限制、哪些需要用户决定（如重复文件是否删除、是否上元数据补全）。

## 15. GET 不要有副作用；调用外部脚本要排队（v1.8 评审）

「读清单」接口里顺手调了 `recommend.py sync`（因为它会重建清单）。后果：一个 GET 会 spawn 子进程、可能触发网络抓取、还会整份重写文件；并发打开页面时两个 sync 同时写同一份 iCloud 文件（它用的是非原子 `open(w)`），中途被杀就可能截断，而后续逻辑还在按截断内容翻转勾选。

**做法**：读接口默认纯读；需要刷新时用显式参数（`?sync=1`）；所有对外部脚本的调用走同一条串行队列；写盘前先校验文件完整性（缺章节标记即判不完整并中止），并且"同步失败"要**在改数据之前**返回。

## 16. 前端改了必须递增 `?v=`（v1.8 评审）

`index.html` 里 `app.js?v=3` 从 v1.5 起就没再递增，其间 v1.6–v1.8 改了 6 次 `app.ts`——浏览器可能一直用旧 JS，新面板根本不出现（本地 headless 每次都是新 profile，所以测试看不出来）。
**做法**：改 `app.ts`/`read.ts` 就递增对应 `?v=`（本次 `app.js?v=8`、`read.js?v=6`）；判断依据是 `src/web/read.ts` 与 `read.html` 的 mtime 关系。已在 RUNBOOK §3.9 写成检查项。

## 17. 测试别仿写外部脚本；UI 断言要等"界面状态"（v1.8 评审）

**仿写 vs 真实**：为了让「待下载确认」能离线测试，我在 `test/helper.js` 里照 `recommend.py` 仿写了一个 stub。结果 API 测试跑的是 stub 生成的**简化清单结构**（无月份分组、无实体转义、无 unavailable 过滤），与生产文件结构不同——7 条用例全绿，却完全没覆盖真实解析路径。
**做法**：把**真实脚本复制进临时目录**跑（`recommend.py` 只依赖 `YABOOK_WATCH`/`YABOOK_RECFILE` + 同目录 json），删掉仿写实现；**必须同时把 `YABOOK_WATCH` 指向临时目录**，否则脚本会去读写仓库里真实的 `tiers.json`（已用 mtime+md5 断言其不变）。

**等界面还是等磁盘**：我加了 `waitFor()` 后只等 `tiers.json` 变成 tier3 就继续点击，结果界面列表还没刷新，下一次点击落到**过期行**，把 bookId 点错了 → 偶发失败。
**做法**：UI 测试的等待条件要盯**用户能看到的状态**（列表条数/元素出现），磁盘断言放在其后作为独立证据；`waitFor` 超时即失败，绝不"重试三次就算通过"。

## 18. 共享弹层的文案必须由调用方驱动（v1.8.1，用户报告）

我把「待下载确认」的二次确认复用了原来的**下载确认弹层**，只替换了正文 `#confirmText`——标题「确认下载」、说明「将真实调用雅书管道下载并归档」、按钮「开始下载」全是写死的。于是用户点「不要了」时，看到的是"标题说下载、正文说不要了"的自相矛盾界面。

**做法**：共享弹层的**标题、说明、按钮文案都做成必填参数**（`confirmReco({title, okLabel, hint, text})`），再包一层语义化函数（`rejectConfirm` / `downloadConfirm`）——从类型上就不允许"只改正文"；并加断言：两种动作的标题与按钮文案**不得相同**、拒绝弹层里**不得出现下载话术**。

**另一条同源教训**：偏好恢复要早于任何 `savePrefs()`。启动流程里 `switchTab()` 会保存偏好，我把「立即下载」的恢复放在它之后就等于用默认值把用户选择覆盖了（表现为"勾了刷新又变回没勾"）——把恢复提到模块初始化处，并用"刷新后仍保持"的断言守住。

## 19. 原子替换会让 `fs.watch(文件)` 失效（v1.9.6）

管道写 `book_meta.json` 用的是 `write(tmp)` + `os.replace(tmp, path)`（**原子替换**，好处是读者永远看不到半截文件）。但 EBM 用 `fs.watch("book_meta.json")` 监听**文件本身** —— 替换后 inode 变了，监听器还挂在已被删除的旧 inode 上，**从此再也收不到事件**。

表现极具误导性：数据明明已改对（磁盘上 888 字），界面一直显示旧值（397 字），`touch` 也没用，**重启即好**（重启会重建监听）。

**做法**：
- 监听**所在目录**并按文件名过滤（目录不受文件替换影响），或每次事件后重建监听器；
- 再加一层**低频 mtime 轮询兜底**（30s），因为网络盘/某些文件系统的事件并不可靠；
- 轮询里比较 mtime，只有真变了才重建索引，避免目录里其它文件（日志/报告）频繁触发。

**通用教训**：凡是"别人原子写、我监听变化"的集成点，都不能只 watch 文件；同一类陷阱还出现在 `.tmp` 中间文件的噪声事件上（要按文件名过滤）。
