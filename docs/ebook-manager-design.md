## 一、目标与范围

基于现有资产（iCloud 书库 + 雅书自动管道 + 已有元数据），构建一个局域网 + 外网可访问的电子书管理器：

- ✅ 快速搜索（书名/作者/分类/标签/豆瓣评分）
- ✅ 分类浏览 + 新书速递
- ✅ 下载到设备（浏览器下载 + OPDS 订阅）
- ✅ 浏览器在线预览（PDF/EPUB）
- ✅ 雅书推荐清单网页化，勾选一键下载
- ❌ 不做：用户体系/多用户、全文检索（二期可选）、书库体检视图（未选，预留）

## 三、架构

```
                         ┌── 家里内网设备（Mac/iPhone/iPad/PC）
                         │    http://<mac-host>.local:6722  （千兆直连）
                         │
浏览器 UI ──► Node 服务 ──┤
 (pdf.js/foliate-js)     ├── Tailscale 设备（出门在外）
                         │    http://<tailscale-ip>:6722 （直连/中继）
                         │
                         └── 任意公网设备
                              https://ebm.example.com  ──Basic Auth──►
                              ECS nginx (<ecs-host> <ecs-ip>)
                                └─反代──► Tailscale ──► <mac-host>:6722

Node 服务（只读）──► iCloud 书库 ~/Library/Mobile Documents/com~apple~CloudDocs/eBooks
Node 服务（subprocess）──► python3 yabook_watch/download_books.py --ids …（仅一键下载时触发）
```

原则：
- 书库**唯一真源**在 Mac iCloud 目录，服务只读扫描，不移动不改名
- 服务 `listen 0.0.0.0:6722`，内网/Tailscale 双网络天然覆盖，一套代码两个入口
- ECS 只做入口反代，零业务逻辑；公网侧 Basic Auth，Mac 服务零认证（保持局域网直接可用）
- 未来加 NAS 副本（形态 3）或换入口，服务代码零改动

### 关键行为

1. **扫描与索引**：启动全扫（805 文件，亚秒级）+ `fs.watch` 增量更新 → 新书由雅书管道落地后**自动出现在网页**，无需任何手动刷新。内存索引即可，无需数据库。
2. **文件名解析规则**：
   - `《书名》作者【…】.pdf` → 书名+作者
   - `书名 - Author.epub`、`书名.pdf` 等变体逐级兜底
   - join `post_details.json`（按 id）→ 豆瓣分/简介/标签（覆盖管道接触过的 193 本，其余仅文件名信息，UI 明示"无元数据"）
3. **搜索 API**：`GET /api/search?q=…`，书名/作者/分类/标签/简介子串匹配（805 本规模毫秒级）
4. **下载**：`GET /api/file?path=…`（路径白名单校验，必须位于书库根内，防目录穿越），`Content-Disposition` 带规范文件名
5. **在线预览**：pdf.js 走 HTTP Range Request（服务端需支持 `Accept-Ranges`，避免大 PDF 全量载入内存）；EPUB 用 foliate-js
6. **OPDS 1.2**：`/opds`（根分类）→ `/opds/category/:name`（书目）→ `/opds/search?q=`（搜索）；iPad 装 Kybook/Chunky 等客户端订阅即用
7. **新书速递**：首页 tab，按文件 mtime 倒序 + 管道 `state.json` 的下载记录
8. **推荐清单一键下载**：读 `tiers.json` + `post_details.json` 渲染 tier2/3 列表（含豆瓣分/判断理由/简介）→ 勾选 → 二次确认弹窗 → subprocess 执行 `download_books.py --ids …` → 成功后串联 `move_to_icloud.py` → fs.watch 自动刷新。前端展示实时输出日志
9. **安全边界**：
   - Mac 服务本身无认证（用户明确要求局域网直接可用）
   - 文件接口有路径白名单防穿越
   - 一键下载有二次确认（防误触真实消耗雅书账号）
   - 公网侧由 ECS Basic Auth 保护
10. **封面（v1.3 新增）**：PDF 用 macOS `sips` 渲染首页、EPUB 解出内嵌封面图，缓存于 `ebm/covers/`（key=rel|mtime，自动失效）。**云端书不生成**——`/api/cover` 对 dataless 直接 404，绝不触发取回（策略 A 红线）；书被打开取回落地后由 fs.watch → refreshCovers 自动补上。OPDS 仅为本地书提供封面链接（防 Kybook 等客户端批量拉图触发取回）。前端卡片左侧 66×92 封面，无封面显示书名首字渐变占位块。
11. **PDF 阅读器 v2.5（v1.4/v1.5）**：虚拟化渲染（IntersectionObserver ±2 屏，canvas 用完即释放，内存恒定 ~30MB）；**教训**：read.html 独立于 app 样式，曾漏定义 `.hidden` 类导致 epubbox 白层永久盖住 PDF（DOM 全对、屏幕全白），后以 CDP 截图+像素分析作为阅读页验收标准；应用壳文件带 `Cache-Control: no-cache`，脚本引用带版本号。导航：右下悬浮 ☰（内嵌书签目录，无书签回退页码网格）/ ⌃ 回第 1 页，顶栏页码可点击输入跳页，Home 键回顶，Esc 关目录。**阅读体验（v2.5）**：**默认"适合整页 + 单页模式"**（v2 默认，贴近翻书习惯），缩放档位（适合宽度/适合整页/100%/125%/150%）+ −/＋ 微调（10%，25%~400%）+ ⌘±/⌘0；单页翻页（←/→、空格、点两侧、左右滑动）；**续读**（滚动/翻页去抖 3s 上报 `pagehide` 兜底，打开自动跳回上次页码并提示）；打开阅读页自动标记"在读"，工具栏可"移出在读"。
**阅读习惯记忆**：缩放与模式存本机 `localStorage.ebm.reader`（带 `v` 版本号）；**用户一旦改过就完全沿用其选择**，版本升级只在无 v/旧 v 时套用一次新默认（避免旧默认被永久固化成"用户选择"）。
12. **书架与偏好（v1.5）**：三书架（在读/喜欢/读完），一本书可多归属，标"读完"自动移出"在读"；侧边栏"我的书架"与"分类"**叠加**筛选；书卡常驻 📖/♥/✓ 切换（乐观更新、失败还原）；"在读"按最近打开倒序并显示"读到 P75 · 继续阅读"。
    - **数据存服务端** `ebm/data/shelves.json`（多设备共享、清缓存不丢）：内存态 + 300ms 去抖落盘 + `tmp+rename` 原子写 + SIGTERM 兜底 flush + 损坏文件隔离为 `.corrupt-<ts>` + 空记录回收 + 写盘失败不影响服务
    - API：`GET /api/shelves`、`POST /api/shelves`（`{rel,shelf,value}`）、`POST /api/shelves/progress`（`{rel,page}`）；参数非法一律 400
    - **偏好存本机** localStorage `ebm.prefs`（tab+书架+分类）与 `ebm.reader`（缩放+模式）；首次进入：在读非空→在读，否则→新书速递
    - 失效记录（书已移走）保留在文件中但界面不显示，不自动删除（数据安全优先）
    - **重置书架数据**：先 `launchctl bootout gui/$(id -u)/com.ebm.server`（等进程退出，否则 SIGTERM 会把内存态写回），再改 `data/shelves.json`，最后 `launchctl bootstrap`
13. **书卡显示规范（v1.5 重排，解决"按钮被压缩 + 内容堆叠"）**：固定六层结构，每层只放一类信息——
    ① 标题行：书名（最多 2 行，超出省略）+ 右上角书架三态图标（26px，未选中 .55 透明）
    ② 作者（灰色小字）
    ③ 信息行：`豆瓣 8.9 · 分类 · PDF · 1.2 MB · ☁ 云端`（**单行省略**；云端状态收进此行，不再给每张卡各加一行芯片）
    ④ 状态芯片：仅"读到 P75"这类真正需要一眼看到的动态状态
    ⑤ 简介：2 行截断（可省略）
    ⑥ 操作行：`📖 阅读`/`▶ 继续阅读`（主按钮，`flex:1` 撑满剩余）+ `⬇ 下载`（次按钮，固定 ~73px）
    布局规则：卡片最小宽 285px；按钮 `white-space: nowrap`，阅读按钮 `flex:1 1 auto`、下载 `flex:0 0 auto`，**操作行永远单行不压缩**；书架图标移出操作行，避免五个元素抢宽度。
    验收：`npm run test:ui` 含 7 项几何断言（无横向溢出 / 两按钮最小宽 ≥70px / 操作行不换行 / 信息行单行 / 书名 ≤2 行 / 书架图标不在操作行 / 窄屏 820px 复测）。真实 1059 本书、桌面 1500px 与 iPad 竖屏 820px 下均为 0 溢出、0 压缩、0 换行。
14. **页面骨架与吸顶规则（v1.5 修复）**：
    - `html { height: 100% }` + `body { min-height: 100% }`——**body 绝不能用 `height: 100%`**，否则顶栏的 `position: sticky` 被限制在视口高度的盒子里而失效（症状：滚动后搜索框消失）
    - **顶栏**（含搜索框）常驻：`position: sticky; top: 0; z-index: 10`
    - **侧边栏整体吸顶**：`position: sticky; top: 62px; max-height: calc(100vh - 62px); overflow-y: auto`；**不要在各组导航（.cats）上单独 sticky**——两个组各自 sticky 会在滚动时互相叠加（v1.5 修复的实际 bug）
    - 窄屏（≤760px）：侧边栏改为普通文档流（横向标签），不吸顶
    - 验收：`npm run test:ui` 断言——滚动后书架/分类重叠像素 = 0、顶栏 sticky `top` 保持 0、侧边栏不钻到顶栏下方
15. **书库增量渲染 + 无限滚动（v1.5）**：首屏只渲染 120 张（`PAGE_SIZE`），**滚到接近底部自动追加下一屏**（`IntersectionObserver` + `rootMargin: 600px`，无需点击）；「显示更多」按钮保留作兜底（键盘/无障碍/自动加载未触发）。筛选或搜索变化时回到一屏——若此时视口仍在底部，会自动补齐到填满视口（预期行为）。搜索始终作用于全部书籍，不受已渲染数量限制。
    验收：`npm run test:ui` 断言——首屏 120 张 / 滚到底自动追加 / 连续滚动可加载完全部 / 全部加载后按钮隐藏 / 顶部时筛选回到一屏 / 手动按钮兜底可用 / 搜索命中未渲染的尾部书籍。真实 1059 本书实测：每次滚动自动 +120（120→240→…→840），零 JS 异常。

16. **图书详情（v1.5）**：点击卡片空白处（或卡片聚焦后回车/空格）打开详情弹层——大封面、**完整简介（不截断）**、目录、元数据（出版社/译者/页数/出版日期/豆瓣）、标签、书架三态、阅读/下载、文件路径；✕/Esc/点遮罩关闭。
    - **接口分层**：`/api/books` 保持轻量（简介截断 300 字，不含目录/meta）；`GET /api/book?path=` 单本按需返回完整字段。实测 1059 本下 `/api/books` 仍为 447KB，目录零泄漏到列表。
    - **实体解码**：管道 intro/toc/meta 大量含 `&ldquo;` `&hellip;` `&mdash;` 等命名实体，原实现只覆盖 7 个 → 292 本书的简介在页面上显示成 `&ldquo;` 字样。现已在服务端统一按"命名实体表 + 数字实体"解码，前端再兜底一层；实测残留 0。
    - **数据现实**：仅 197/1059 本带管道元数据（简介 196 本，源数据最长约 1500 字；106 本的列表简介被 300 字截断，详情可见完整版，如《徐霞客游记》300→383 字）。其余书籍详情页展示文件名派生的信息，UI 明示"暂无简介"。
    - **搜索语义（v1.5 修正）**：搜索始终覆盖全库——① 新书速递中不再受"最新 60 本"切片限制；② 有搜索词时暂时忽略书架/分类筛选并显示提示条（清空搜索即恢复）。修复"筛选叠加后书莫名搜不到"（如"在读"筛选下搜其他书返回 0）。

## 四点五、文件名清理（v1.5）

**背景**：雅书下载器把来源标记写进文件名，如 `《书名》作者【文字版_PDF电子书_雅书】.pdf`（391 本）、变体 `【文字版_PDF电子书_下载】`（19 本）、`【扫描版_PDF电子书_下载】`（1 本）。

**清理规则（只动管道标记，绝不动正文括号）**：仅当 `【…】` 内容含 `雅书|电子书|文字版|扫描版|精校版` 时才移除，随后清理残留的 `_`/空格。因此 `【美】``【英】``【2022新书】``【中文版】` 等**内容性括号全部保留**（已用 7 条单测锁定）。

**已有文件（2026-10-01 执行）**：计划 411 本 → 实际改名 **410 本**（含 1 本金丝雀先行验证），跳过 1 本（与已有同名文件字节数完全相同，属重复下载）。映射文件 `ebm/data/rename-map-*.json`；回滚脚本 `ebm/scripts/revert-rename.py`（默认干跑，`--apply` 才执行）。
- **iCloud 安全**：改名是元数据操作——金丝雀实测 `blocks` 前后均为 0（**不触发云端取回**），文件 size/mtime 不变；整批改名前本地 56 / 云端 1003，改后完全一致。
- **配套修复**：索引的"按文件名回退匹配"原用管道 `state.json` 里的旧文件名 → 改名后 64 本书元数据失联（197 → 133）。改为双方都做**标记归一化**（`normBase`）后恢复 197/197。
- **书架/进度迁移**：`shelves.json` 的 key 是相对路径，改名后需同步（23 条记录中 7 条已迁移，0 条失联）；操作必须在服务停止时做（否则 SIGTERM 兜底会把内存态写回）。

**重复文件清理（2026-10-01）**：`科普/《数学的100个基本问题（新版）》靳平.pdf` 与带标记的那份字节完全相同（8,858,376 bytes，两次下载差 13 天）→ 删除带标记的那份，书库 1059 → 1058。
- **操作教训**：`shutil.move`/`mv` 跨卷（iCloud Drive → ~/.Trash）会退化成**复制**，而复制 dataless 占位文件会失败（`Resource deadlock avoided`）。正确做法是 **Finder 删除**（iCloud 感知，文件进 iCloud「最近删除」，30 天内可恢复）：`osascript -e 'tell application "Finder" to delete (POSIX file "..." as alias)'`；或在同一卷内重命名绕过扫描器。

**未来自动处理**：落地点是管道归档那一步 `yabook_watch/move_to_icloud.py`（"存储时即干净"）——新增 `clean_filename()`，并把目标判重改为"同名同大小才跳过、同名不同大小加 (2)(3) 序号"，避免静默丢书；路径支持环境变量覆盖以便隔离测试。`match_posts.py` 本就剥离 `【.*?】`，无需改动。

## 四点六、书目元数据补全集成（v1.6）

**问题**：雅书帖常只有书名没有简介；原有元数据只覆盖 19%，看书的人无法判断是否值得读。

**方案**：另一套体系（管道侧，见 [metadata-enrichment.md](metadata-enrichment.md)）按五层来源逐层降级取简介——
L1 雅书详情页（零网络）→ L2 豆瓣 suggest + 详情页 → L3 OpenLibrary（走代理）→ L3b Google Books（需 API key）→ L4 arXiv；
中文书名走 L2→L3→L3b→L4，外文走 L3→L3b→L2→L4，文件名带 arXiv ID 优先 L4。
产出统一落在 `yabook_watch/book_meta.json`，**key 就是书库相对路径**（实测 100% 命中），另有 `meta_cache.json` 缓存（失败也缓存、可断点续跑）。

**ebm 侧只做两件事**：

1. **消费**（`src/indexer.ts`）：读 `book_meta.json` 按 `rel` 命中，**只填空不覆盖**（雅书精确匹配优先）；随文件 mtime 自动重载（补全任务后台持续写盘，重建索引即生效）。
   字段映射：`intro`→列表(300 字)/完整(6000 字)、`toc`、`tags`、`douban`（`0.0` 视为无评分）、`year`→`pubDate`、`publisher`、`translator/pages/original_title/isbn/author_bio`→`meta`；新增 `metaSource` 供详情页显示「简介来源」。
   - 复用 `htmlUnescape()`（285 条记录含 `&ldquo;` 等实体）
   - **过滤 arXiv 脏值**：arXiv 来源把 arXiv ID 写进 `author`（`2308.11432v7`），不作为作者采用
2. **触发**：`GET /api/metadata/status`（覆盖率/来源/待补清单/外部进程状态）+ `POST /api/metadata/run`（`tasks=[build|enrich|catalog]`、`limit`，流式日志，结束后自动重扫重建）。UI 入口：顶栏「🗂 元数据」面板 + 书库顶部「检测到 N 本新书还没有简介」提示条（**用户点击触发，不在 fs.watch 里自动跑**，避免大批拖书时发起几百次外部请求）。

**红线与护栏**：
- 不改管道侧 `.py`（被每日 8:00 巡检共享）；不重写匹配/限速逻辑
- **绝不同时跑两个 `meta_enrich.py`**：两者都是"读整份 → 内存改 → 整份写回"，会互相覆盖。因此新增 `src/jobs.ts` 全局锁（下载与元数据任务串行），并检测外部进程 → 触发返回 `409`
- 不为了元数据取回 iCloud 文件（策略 A）
- `introFull` 不进 `/api/books`（列表仍轻量）

**效果**：有简介的书 **196/1058（19%）→ 795/1100（72%）**；来源：豆瓣 407 · 雅书 353 · arXiv 60 · OpenLibrary 11。

## 四点七、待补清单与人工覆盖（v1.7）

**动机**：管道按"宁可不补也不错"打分（≥88 分，或有作者佐证 ≥75），会把**其实同一本但标题有差异**的候选拒掉——实测 31 本属此类（《安全边际》→"安全边际" 83 分、《接话破冰》86 分、《给久坐者的12堂体态纠正课》→"给久坐者的12堂体态课" 73 分）。这些书并非"找不到信息"，而是"找到了被规则放弃"。

**方案（管道文件零改动）**：
1. **可见**：`GET /api/metadata/gaps` 按真实缓存说明分类：`near_miss`（有同书候选但分数不足）· `low_score`（<70 疑似不同书）· `no_candidate`（豆瓣无候选）· `partial`（只补到作者/年份）· `throttled` · `no_entry`（未登记）· `other`；已有简介与已覆盖的书自动排除，`near_miss` 优先展示。
2. **可修**：`POST /api/metadata/candidates` **复用管道自己的 `search_queries()` + `douban_pick()`**（通过 `python3 -c` 调用其模块，不修改其文件）返回候选 id/分数；`POST /api/metadata/adopt` 抓豆瓣详情写入覆盖；`POST /api/metadata/override` 手工填写；`DELETE /api/metadata/override` 撤销。
3. **存储**：`src/overrides.ts` → `data/meta_overrides.json`（原子写 + 损坏隔离 + SIGTERM 兜底），**优先级最高**（`人工覆盖 > book_meta.json > post_details.json > 文件名解析`），且与管道数据物理隔离——管道再次补全不会覆盖人工确认。
4. **UI**：面板内「待补清单」逐条 `查候选 / 手动补 / 撤销覆盖`；候选列表显示 id/作者/年份供人工判断是否同一本书。

**首例效果**：《给久坐者的12堂体态纠正课》采纳豆瓣 36538507 后获得 396 字简介 + 豆瓣 7.8 + 华龄出版社 + 译者/268 页/ISBN + 作者简介，来源标记「douban（人工确认）」。

**遗留（管道侧，已定位未改）**：`meta_enrich.py` 的 Google Books 层查询写成 `q=intitle:"<书名>"`，实测 HTTP 200 但 items=0；去引号后有效（Sous Vide at Home 1545 字、Deep Learning 1301 字），但会把 `Introduction to Agents` 错配成 `Introduction`，因此修查询的同时必须保留严格打分。Google Books 必须走代理（直连 `No route to host`）。

## 四点八、书名 / 文件名 / 元数据编辑（v1.7.3）

**动机**：书库信息来自下载站点与外部源，书名常被"作者+出版社+年份"污染（实测 172/1114，15%），文件名也残留站点标记。用户需要一个**有限但够用**的编辑入口。

**范围（用户确认）**：书名与文件名**分开**编辑（另给"同时重命名"复选框）；副本序号只提示不自动改；先做单本，批量留后。

**设计要点**：
1. **清理规则可解释**：`suggestFileName()` 返回 `{suggested, title, rules[], notes[]}`，界面把"旧 → 新"与命中规则都摆出来，用户确认后才执行；含糊内容（`(1)`、英文 `_`）只提示
2. **书名 ≠ 文件名**：书名**保留空格**（`_`→空格、不引入 ` - `），像 `COVID-19` 的词内连字符不动；文件名允许 ` - ` 作分隔
3. **改名不丢信息**（最关键）：rel 是书架/进度/覆盖/管道元数据的共同键 → 改名时迁移 `shelves.json`、`meta_overrides.json`，并写 `data/path-aliases.json` 别名链，索引器 `pathAliases.resolve()` 跟随链查回 `book_meta.json`/`post_details.json`
4. **安全边界**：只 `rename` 不读内容（iCloud 占位文件安全）；扩展名一律沿用；目标同名拒绝；日志复用既有 `rename-map-*.json` 格式 → `scripts/revert-rename.py` 可直接回滚
5. **反向收益**：清理后的文件名往往**更容易匹配上**管道元数据（实测《健身笔记》改名后从 0 字简介变成 344 字）

**遗留**：批量模式（勾选多本 → 批量清理/批量改书名）按用户要求暂缓；分类/移动文件夹、自定义封面不在范围内。

## 四点九、待下载确认进界面（v1.8）

**问题**：每日巡检把 T2 待定书写进 `_推荐待确认.md`，人工勾选后**还要手动跑 `apply`**；界面上的「推荐清单」则是 tier2+3 的 336 本混合列表（288 本是已拒绝的历史），且无法批准/拒绝写回。

**方案（A：管道零改动）**：
1. **清单**：仍由 `recommend.py sync` 生成 —— EBM 读取时先 sync（保留手写勾选），解析「## 待确认」区（严格复用管道 `LINE_RE`，表格里的 `[ ]` 不会误认）
2. **决策**：EBM 只翻转对应行的方括号字符（`flipMarks`：只改待确认区、只改指定 id、其余字节不动、幂等），再调 `recommend.py apply`；批准→tier1、拒绝→tier3+「用户拒绝」全部由管道完成
3. **并发**：与下载/元数据任务共用 `jobs.ts` 全局锁（409）；提交前校验 id 仍在清单里（防幽灵提交）；脚本缺失 → 502 且界面只读提示
4. **界面**：Tab 改名「待下载确认」，条目含建议归档目录/判断理由/作者·日期/简介/豆瓣；批量 + 单条动作；「不要了」「确认并立即下载」有二次确认

**互操作**：Markdown 仍是同一份真源，手机/Obsidian 勾选有效（但两种方式别同时操作同一批）。

## 四点十、推荐清单的量级边界与历史归档（v1.9）

**量级事实**：管道 `recommend.py sync()` 写清单时 `lines += processed[-200:]` —— 「已处理」区**最多 200 条**，因此文件天然有界：实测 200 条已处理 ≈17 KB，加待确认区（每条 ≈290 字符含简介），稳态 **20~50 KB / 300~600 行**，极端（200 条待确认）也只有 76 KB / 830 行。EBM 侧解析是一次线性扫描，千行内亚毫秒；主要延迟来自 iCloud 往返，与文件大小几乎无关。

**阈值（进入下一档才考虑改设计）**：文件 >200 KB、待确认 >100 条、解析 >200 ms —— 目前有 ~20 倍余量，**不建议**为性能换掉 Markdown（会失去"随时人工查看 + 手机勾选"这两个已被验证的价值）。

**归档（EBM 侧，管道零改动）**：每次刷新清单（sync 之前）把「已处理」条目按条目日期分月追加到 `data/reco-archive/reco-archive-YYYY-MM.md`：只追加、按行去重、幂等。主清单保持 ≤200 条、小而快；历史按月分片、仍是 Markdown、可直接人工查阅。界面显示 `清单 X KB · 历史已归档 N 条`，并在超阈值时提示。

## 四点十一、撤销「不要了」与数据所有权（v1.9.2）

**背景**：`tiers.json` 原本只由管道 `recommend.py` 写（`apply()`：批准→tier1、拒绝→tier3+folder 置空+note 追加"用户拒绝"）。用户希望误拒绝能在界面上撤销（选项 A，已确认）。

**设计**：EBM 增加**唯一一条**写 `tiers.json` 的路径 `POST /api/reco/restore`，并以四重保护约束风险：
1. **拒绝前快照**：`decide` 在调用 `apply` 之前，把被拒绝书的原 `tier/folder/note` 存入 EBM 自己的 `data/reco-restore.json`（否则管道已把 folder 置空，无法还原）
2. **字段级最小写**：只改指定 id 的 `tier/folder/note`，其余条目与字段原样保留；note 中的拒绝标记会被清理（重复拒绝也能恢复）
3. **原子写 + 备份**：`tmp + rename`；每次写前复制到 `data/tiers-backup/tiers-<ts>.json`（保留最近 5 份）
4. **共用互斥锁**：与下载/元数据任务串行，避免并发写坏

**边界**：界面外发生的拒绝（例如手工编辑）也能恢复，但只能清除拒绝标记、目录无法还原（无快照）。

## 八、验证方法

### 自动化（每次改动都跑，v1.5 建立）

```bash
cd ebooks/ebm
npm test          # 构建 + 25 项：存储层单元测试(10) + HTTP 契约/稳定性测试(15)
npm run test:ui   # 浏览器端验收 32 项：无头 Chrome + 隔离实例 + 截图像素（不碰真实数据）
```

- **存储层单元测试**（`test/shelves.test.js`）：并发 50 条不丢、200 次高频写只留一条、损坏 JSON 隔离降级、只读目录写失败仍可用、人工改坏字段被过滤、重启数据仍在
- **HTTP 契约与稳定性**（`test/api.test.js`）：Range 分段/越界 416、路径穿越拒绝、并发读 100 + 并发写 30、**重启后书架与进度仍在**、数据文件被外部写坏后重启仍可用、异常请求体不产生 5xx、书库新增文件 15 秒内被索引
- **浏览器验收**（`scripts/ui-check.mjs`）：书架计数与持久化、偏好恢复、默认进入规则、缩放档位（100% = 816px 原始尺寸）、适合整页不超一屏、单页模式与键盘翻页、续读跳回、模式记忆、**canvas 墨迹像素**与整页白屏回归

### 人工验收清单（Mac Chrome / iPad Safari 各一遍）

1. 打开书库 → 记住的视图自动恢复；首次打开落在"在读"（非空）或"新书速递"
2. 任意书卡点 📖/♥/✓ → 侧边栏计数即时变化；刷新后仍在
3. 标"读完" → 自动离开"在读"，仍能在"书库"搜到
4. 打开一本 PDF → 顶栏出现缩放工具条；切"适合整页"一屏看全页；切"单页模式"用 ←/→ 翻页（iPad 用左右滑动）
5. 读到第 10 页左右关掉 → 重新打开 → 自动跳回并提示"已跳到上次读到第 N 页"
6. iPad：横竖屏切换后书页宽度自适应；双指缩放由系统浏览器负责
7. 云端书：列表显示"☁ 在云端"，打开时显示取回进度，取回后封面自动出现
