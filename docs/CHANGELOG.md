## v1.15.0 · 基本信息改两列自适应布局（左侧空白收敛）
**2026-10-31**

### 用户问题
详情页基本信息原为**单列**（最多 12 行），内容短、右侧大片空白，浪费空间。

### 完整字段枚举（最多 **12 行**）
| 来源 | 字段 |
|---|---|
| 列表数据 | 分类 · 格式 · 豆瓣评分* · 数据位置 · 文件时间 · 阅读进度* |
| 详情元数据 | 原名* · 译者* · 页数* · 出版日期* · 出版社* · ISBN* |
（带 * 的按是否有值显示；实测常见 9~11 行）

### 实现
- `.dinfo` 改为 **CSS Grid 两列**（`repeat(2, minmax(0,1fr))`，列间距 16px）
- **长字段自动跨两列**：值长度 >26 字（长原名、长出版社等）时加 `.wide` → `grid-column: 1 / -1`，不挤压相邻单元
- 窄屏（≤620px）自动回落单列
- 顺带修正 `#dInfo` 重复渲染调用

### 实测效果
| 指标 | 改前 | 改后 |
|---|---|---|
| 信息区高度（同一本书）| 297px | **240px** |
| 列数 | 1 | **2** |
| 长原名 | 单行占满整行但右侧空白 | **自动跨两列，无空白** |
| 简介/目录位置 | — | 上移约 57px |

### 验证
- 截图实测：原名（26+ 字符）跨两列，其余成对排列 ✓
- `npm test` **121/121** · `npm run test:ui` 见下（新增：基本信息为两列、长字段自动跨两列）

## v1.11.1 · 修复：转换出的 EPUB 没有封面 → 电纸书列表里所有书缩略图一样
**2026-10-30**

### 问题（用户报告）
用户把 4 本书转成 EPUB 推进电纸书后，**列表里所有书的图都一样**，和各自封面不符。

### 根因
`pdf2epub.py` 生成的 EPUB **没有内嵌封面**（无 `cover.jpg` / 无 `properties="cover-image"` / spine 无封面页）✗
→ 电纸书只能回退到**统一的默认占位图**，所以 4 本看起来一模一样。
（实测确认：修复前 4 个 EPUB 里 `有封面元数据: False`）

### 修复（转换器 v3）
- **自动取封面页**：默认第 1 页；若几乎全白（空白衬页）自动往后找前 6 页中第一张有内容的页
- 渲染 **150dpi JPEG**（`EBM_CONVERT_COVER_DPI`/`EBM_CONVERT_COVER_QUALITY` 可调）写入 `OEBPS/cover.jpg`
- OPF 声明：`<meta name="cover" content="cover-image"/>`（旧阅读器兼容）+ `properties="cover-image"`（EPUB3）
- 新增 `OEBPS/cover.xhtml` 并置于 **spine 首位**
- 顺带补 EPUB3 必需的 `<meta property="dcterms:modified">`
- 接口回传 `hasCover` / `coverPage`；转换结果区显示「含封面 / 无封面」

### 验证
| 项 | 结果 |
|---|---|
| 真实书（《力量训练基础》226 页）| 提取封面 **975×1388 · 197KB**，`open` 检查为真实封面图 ✓ |
| 用户那 4 本重转 | **4/4 均带封面**（147~249KB）✓ |
| `npm test` | **121/121**（convert 测试新增：cover.jpg/cover.xhtml/cover-image/meta cover/spine 首位）|
| 部署 | 2026/10/30 19:50:15 |

### 用户需要做的
1. 重新转换（已替他重转那 4 本）
2. 阅读器上**先删掉旧的那 4 个文件**再重新接收（设备按文件缓存缩略图，同名覆盖可能仍显示旧图）
3. 推送时先在阅读器打开「传书」页面，并在网页顶栏「📤 阅读器」更新当前地址（端口每次可能不同）

## v1.10.5 · 修复元数据"同名错配"（豆瓣同名不同书）
**2026-10-28**

### 问题（用户报告）
新下载的《更壮 更瘦 更强 身体革命，健身见真我》（Michael Matthews 的中译本）**元数据匹配到了错误的书**：
- 实际匹配到豆瓣 **37367267**《身体革命》（原作名 *Intermittent Living*，作者 **Siebe Hannosset**，国文出版社 2026）✗
- 正确条目应为 **27107200**《更壮 更瘦 更强：身体革命,健身见真我》（Michael Matthews，机械工业出版社 2017，原作名 *Bigger Leaner Stronger*，7.5 分，ISBN 9787518925094）✓
- 导致简介/作者简介/ISBN/评分全部错误（用户核对了豆瓣英文版 11525121，确认是中译本）

### 根因（用管道真实逻辑复现）
`yabook_watch/meta_enrich.py` 的匹配有三个缺陷：
1. `search_queries()` 把书名按空白拆成**碎片查询词**（`更壮`/`更瘦`/`更强`/**`身体革命`**），
   `身体革命` 搜到了同名但完全不同的书《身体革命》✗
2. `title_segments()` 把**副标题碎片**（"身体革命"）当成合法"书名片段"，
   该候选命中 92 分分支；而**正确书**（主标题与文件主标题一致）未命中任何分支，只走相似度评分 ✗
3. `douban_pick()` 的排序键是 `(score, seg_idx)` —— **作者是否匹配完全没有参与排序** ✗，
   于是 92 分的错书压过正确书；片段匹配（92/89）也不要求作者佐证 ✗

### 修复（最小改动，守住"宁可放过不可配错"）
1. **同分时作者优先**：排序键改为 `(score, auth, seg_idx)`
2. **新增前缀分支**：候选标题是文件标题前缀（≥4 字且覆盖 ≥30%）→ 93 分，**需作者佐证**
3. **片段匹配必须有作者佐证**：92（等于标题片段）/89（via）分支在文件有作者时，作者不匹配直接跳过

### 验证与修复结果
| 项 | 结果 |
|---|---|
| 复现（修复前）| 候选含正确书 27107200 三次，但 `douban_pick` 选中 37367267（92 分，auth=False）✗ |
| 修复后 | 选中 **27107200**（93 分，auth=True）✅ |
| 该书元数据 | 已重抓写回：机械工业出版社 2017 · 7.5 分 · ISBN 9787518925094 · 正确中文简介 ✓ |
| EBM 生效 | book_meta watcher 自动重索引，`/api/book` 立即返回新数据 ✓（无需重启）|
| 全库自检 | 517 条已配豆瓣的记录中，标题相似度 <45 的仅 2 条：1 条为本例（已修），另 1 条是同名带 `+` 的标点差异（非错配）✓ |
| 备份 | `yabook_watch/book_meta.json.bak-repair` |

### 新增工具
`yabook_watch/repair_mismatched_meta.py "<书库相对路径>" [--dry-run]`
—— 用修复后的匹配器重新抓取**单本**并原子写回 `book_meta.json`（保留原 path/search_title），EBM 自动重索引。

## v1.10.4 · 修复：书库更新后「新书速递」看不到新书（需刷新浏览器）
**2026-10-28**

### 问题（用户报告）
书库有新书入库后，切到「新书速递」标签看不到新内容，**必须刷新浏览器**。
原因：前端只在 `boot()` 时拉一次 `/api/books`，切标签仅重渲染内存里的旧数组，从不重新取数。

### 修复：按条件判断"内容是否变了"，变了才重新读取
- 新增轻量探针：`GET /api/health`（只返回 `books` 计数，开销极小）
- 三个触发时机：
  1. **切换到「书库」/「新书速递」标签**时（立即渲染 → 后台探测 → 有新书则静默刷新）
  2. **页面重新可见**（`visibilitychange`，切回浏览器时）
  3. **每 30 秒轮询**（仅在页面可见时）
- 仅当服务端计数 > 前端已知数量时才 `fetch("/api/books")` 重新取数并 `renderActive()` 重绘（**保留搜索/书架/分类状态**），并弹提示「书库已更新：新增 N 本」
- 并发保护：`libRefreshBusy` 防止重复请求

### 验证

|---|---|
| 端到端（ui-check 真实模拟）| 主页面加载后 → 服务端新增一本书（写文件，等 watcher 索引）→ 点「新书速递」→ **不刷新浏览器**即出现新书 ✓ |

## v1.9.9 · 更正：下载失败不是"限流"，是脚本「不重试直链 + 网盘通道失效」
**2026-10-22**

### 用户质疑（判断正确）
"这个网站除非一天内大量下载，否则登录条件下不会限流，一定另有原因。"

### 复查：手工复现直接推翻了"限流"结论
用脚本自己的登录态与请求路径，分别请求**失败书(23488)** 与**成功书(23490)**：

| ctfile `get_file_url.php` | **0 字节** | **0 字节（同样为空！）** |

→ 结论：**直链本来是好的**；ctfile 通道对所有书都拿不到 URL（含"成功"的书），与"限流"无关。
真正的两个原因：

### 修复（`yabook_watch/download_books.py`）
- 直链失败后**先重试直链 3 次（20s/40s 递增间隔）**，仍失败才转网盘 ❶
- 直链返回非 PDF 时，错误信息带上 **HTTP 状态 + Content-Type + 页面标题**（不再猜"可能需登录/配额"）
- ctfile 空响应文案改为 **`空响应(HTTP 200, 接口未返回URL)`**，并注释说明**并非限流**、该通道当前对所有书失效、仅作最后兜底

## v1.9 · 推荐清单的量级分析与历史归档（保持有界 + 不丢历史）
**2026-10-12**

### 用户提出
`_推荐待确认.md` 攒着历史与信息，量级大了会不会变慢？是否需要定期拆分/归档，让文件始终不超过一个处理量？

### 实测结论（不是估算）
| 事实 | 数值 |
|---|---|
| 管道 `recommend.py sync()` 对「已处理」区的保留上限 | **200 条**（`processed[-200:]`，第 201 条起被静默丢弃）→ **文件本身有界，不会无限增长** |
| 当前清单 | 25.2 KB / 155 行（已处理 135 条） |
| 单条已处理记录 | 平均 87 字符（单行） |
| 单条待确认 | 平均 290 字符（含作者/简介明细行） |
| 稳态推算 | 200 条已处理(≈17KB) + 100 条待确认(≈28KB) ≈ **47.5 KB / 530 行**；即使 200 条待确认也只有 76 KB / 830 行 |
| 解析/同步成本 | 一次线性扫描，千行内 **亚毫秒**；真正的延迟是 iCloud 往返（百毫秒级），与文件大小几乎无关 |

**因此真正的风险不是"变慢"，而是 ① 超过 200 条的历史被静默丢弃；② 待确认积压影响人工决策。**

### 量级阈值（何时需要变更处理方式）
| 指标 | 舒适 | 注意 | 必须处理 |
|---|---|---|---|
| 主清单文件 | **< 50 KB** | 50–200 KB | **> 200 KB** |
| 待确认条目 | **< 50** | 50–100 | **> 100**（决策效率下降，不是性能） |
| 已处理历史 | ≤200 条（管道上限，自动） | — | 需要追溯更久 → 依赖归档 |
| 解析/sync 耗时 | **< 5 ms** | 10–50 ms | > 200 ms（届时才值得换存储） |

### 新增（EBM 侧，管道零改动）
